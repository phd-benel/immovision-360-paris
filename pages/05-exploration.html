Phase 3 : Exploration (EDA) — du Data Warehouse au diagnostic pour la Mairie

Rappel. Les phases précédentes vous ont mené du Data Lake (fichiers bruts) au pipeline ETL, puis au chargement dans un entrepôt relationnel. Vous savez désormais isoler le périmètre « Élysée », enrichir les données et structurer un schéma SQL. La Phase 3 ne consiste pas à « refaire » l’ingénierie : elle consiste à interroger la donnée déjà consolidée pour répondre aux questions du Chapitre 1 — prix, ressenti, image — avec des graphiques et des chiffres vérifiables.

Pour démarrer l’analyse exploratoire (EDA) sur une base propre et homogène (mêmes types, mêmes contraintes pour toute la classe), nous mettons à votre disposition un jeu tabulaire nettoyé et ses scripts d’import PostgreSQL. Votre première mission dans ce chapitre est de recréer localement ce petit Data Warehouse de référence, puis de vous approprier le dictionnaire des variables : sans cette lecture métier, aucun graphique n’aura de sens pour la Maire.

1. Télécharger le dossier DataWarehouse et importer les données dans PostgreSQL

Téléchargez l’archive DataWarehouse.zip (dossier complet : CSV tabulaire nettoyé, script SQL d’import, fichier d’aide pour la ligne de commande). Décompressez-la à un emplacement fixe sur votre machine (ex. : C:\projets\ImmoVision\DataWarehouse ou équivalent).

Télécharger DataWarehouse.zip

Prérequis. PostgreSQL installé, service démarré, et utilitaire psql accessible dans le terminal (variable d’environnement PATH). Il doit exister une base nommée immovision (créez-la une fois si besoin) et un utilisateur autorisé — en pratique le script d’exemple utilise -U postgres, comme dans le fichier fourni.

Première installation : créer la base immovision

Sous psql en administrateur (souvent utilisateur postgres) : 

CREATE DATABASE immovision;

Quittez puis reconnectez-vous sur immovision pour lancer l’import ci-dessous.

Ouvrez une invite de commandes (cmd ou PowerShell), placez-vous dans la racine du dossier décompressé DataWarehouse, puis exécutez exactement les deux lignes prévues dans sql\postgres\CMD.txt (chemins relatifs identiques sous Windows) : 

cd sql/postgres
psql -U postgres -d immovision -f import_elysee_tabular.sql

Ce script crée la table elysee_tabular et charge le fichier CSV postgres/elysee_tabular.csv. En cas d’erreur d’authentification, configurez le mot de passe PostgreSQL (variable PGPASSWORD sous Windows, ou fichier pg_hba.conf / compte dédié) selon votre installation locale — le support du cours ne peut pas deviner votre politique de sécurité.

Vous pouvez vérifier rapidement que l’import a réussi : 

psql -U postgres -d immovision -c "SELECT COUNT(*) FROM elysee_tabular;"

2. Comprendre le Data Warehouse « clean » : dictionnaire des colonnes

La table elysee_tabular est volontairement compacte : chaque ligne est une annonce du périmètre concerné, avec des champs déjà encodés ou numérisés pour l’analyse (et non plus le catalogue brut des 70+ colonnes d’Airbnb). Avant tout scatter plot ou jointplot, lisez attentivement la signification de chaque variable — notamment les codes entiers, qui ne sont pas toujours des « notes » arbitraires mais des mappings fixes issus du pipeline.

Déplier : description détaillée des colonnes de elysee_tabular

id
Pas une catégorie : identifiant numérique de l’annonce (ex. 2871271). Aucun « 1 = … » ici.

calculated_host_listings_count
Nombre entier (ex. 1, 25, 184) = nombre d’annonces du même hôte. Plus la valeur est grande, plus l’hôte a d’annonces sur la plateforme.

availability_365
Nombre entier de 0 à 365 = jours de disponibilité déclarés sur l’année.
Ex. : 0 → pas ouverte à la réservation sur la période considérée ; 365 → disponible toute l’année (selon la définition Airbnb).

host_response_rate_num
Nombre décimal entre 0 et 100 (pas un code de catégorie) : part des messages auxquels l’hôte répond, comme un pourcentage.
Ex. : 100.0 → 100 % ; 53.0 → 53 % ; vide → pas d’info.

room_type_code (mapping fixe)

Code Signifie (catégorie d’origine Airbnb)
0→ Shared room (chambre partagée)
1→ Private room (chambre privée)
2→ Entire home/apt (logement entier)
3→ Hotel room (chambre type hôtel)
−1→ type inconnu ou valeur non reconnue

host_response_time_code (mapping fixe, ordinal : plus petit = plus rapide)

Code Signifie (catégorie d’origine Airbnb)
0→ within an hour (dans l’heure)
1→ within a few hours (quelques heures)
2→ within a day (dans la journée)
3→ a few days or more (plusieurs jours)
−1→ délai inconnu ou non reconnu

standardization_score (3 valeurs = 3 catégories résumées en chiffre)

Score Signifie (logique pipeline image)
1→ « Appartement industrialisé » (style très standardisé / catalogue)
0→ « Appartement personnel » (plus vécu, moins catalogue)
−1→ « Autre » (pas classable, pas d’image, erreur, etc.)

neighborhood_impact_score (3 valeurs = 3 catégories résumées en chiffre)

Score Signifie (logique pipeline texte)
1→ « Hôtélisé » (processus pro, peu de lien humain, etc.)
0→ « Voisinage naturel » (échanges, vie de quartier, etc.)
−1→ « Autre » (ambigu, texte absent, erreur, etc.)

Une fois la table importée et le dictionnaire assimilé, vous enchaînez avec le parcours d’analyse ci-dessous. Il est découpé en quatre blocs, calqués sur une séance type de trois heures : chaque bloc mélange cours (méthodes, repères professionnels) et travail attendu (consignes, livrable court). Vous pouvez aussi étaler ces blocs sur plusieurs séances selon votre emploi du temps.

3. Parcours EDA — Bloc A : cadrage métier et feuille de route

Idée clé. En entreprise, on ne lance pas matplotlib au hasard : on part des questions métier, puis on choisit les variables et les graphiques qui peuvent y répondre — ou montrer que la donnée ne permet pas encore de trancher. L’EDA exploratoire sert à tester des hypothèses et à quantifier, pas à « prouver ce qu’on veut ».

Méthode. Reprenez le Chapitre 1 (brief de la Mairie). Pour chaque grande question (lien prix / nuisance / standing marketing, concentration des offres, profil « pro » vs résidentiel, etc.), listez les colonnes de elysee_tabular qui en sont des proxies (approximation mesurable). Exemples de lecture : calculated_host_listings_count pour la concentration côté hôte ; availability_365 pour l’usage type location ; host_response_rate_num et host_response_time_code pour un indicateur de réactivité « gestion professionnelle » ; standardization_score et neighborhood_impact_score pour les dimensions image et texte déjà agrégées.

Astuce. Construisez un tableau à trois colonnes : Question ou hypothèse → Variable(s) utilisée(s) → Type de graphique envisagé (histogramme, barres, boxplot, scatter, heatmap de corrélation…). Si une case reste vide, c’est un signal : soit la question n’est pas encore operationalisable, soit il manque une donnée (à dire explicitement dans le rapport).

Consignes (à réaliser en binôme ou individuellement)

  1. Relire le Chapitre 1 et noter au moins trois questionnements du brief que vous comptez traiter avec elysee_tabular.
  2. Pour chacun, associer au moins une colonne du dictionnaire (section 2) et préciser si la variable est identifiant, quantitative, ordinale (codes avec ordre) ou catégorielle nominale (codes sans ordre naturel).
  3. Rédiger en une phrase l’interprétation possible si le graphique allait dans un sens fort (et ce qui invaliderait l’hypothèse).
Livrable du bloc A : une feuille de route d’analyse d’une page maximum (PDF ou markdown dans le dépôt) contenant le tableau « Question → variable(s) → graphique envisagé », plus un court paragraphe sur les limites déjà visibles (ex. pas de prix dans cette table, scores −1 à traiter à part, etc.).

4. Parcours EDA — Bloc B : qualité des données et descriptif univarié

Idée clé. Avant de croiser les variables, le professionnel vérifie la qualité : effectifs, doublons, valeurs manquantes, part des codes « inconnu » (−1 ou NULL). Un graphique sur données sales est une fausse preuve pour le décideur. L’analyse univariée décrit chaque variable seule : distribution, médiane, quartiles pour les numériques ; fréquences pour les codes.

Méthode. Depuis PostgreSQL ou après export vers Python/Pandas, calculez au minimum : nombre de lignes ; unicité de id ; pourcentage de NULL sur host_response_rate_num ; répartition des standardization_score et neighborhood_impact_score (y compris −1). Pour les variables continues ou semi-continues (availability_365, calculated_host_listings_count), regardez les quantiles et l’existence de valeurs très extrêmes. Pour les codes, utilisez des diagrammes en barres avec les libellés métier (pas seulement 0, 1, 2…).

Outliers. Un point « aberrant » statistiquement peut être un cas légitime (ex. hôte avec très nombreuses annonces). En politique de la donnée urbaine, on ne supprime pas toujours : on signale, on segmente (graphique avec / sans extrêmes), ou on garde et on commente. Documentez toute exclusion.

Astuces. SQL permet des profils rapides (COUNT, MIN/MAX, GROUP BY sur les codes). En Python, describe(), value_counts(), et des histogrammes avec bornes explicites évitent les échelles trompeuses. Toujours indiquer n (effectif) sur le graphique ou dans la légende.

Consignes

  1. Produire un mini rapport d’audit : effectif total, contrôle des doublons sur id, taux de manquants et taux de −1 pour les scores et codes pertinents.
  2. Réaliser au moins deux graphiques descriptifs univariés (ex. histogramme de availability_365 ; barres des effectifs par room_type_code avec légende textuelle des catégories).
  3. Pour chaque figure : titre, axes, unité ou échelle, légende lisible par un non-statisticien.
Livrable du bloc B : deux à trois paragraphes rédigés sous forme d’« état des données » (qualité, manquants, codes −1) + deux graphiques descriptifs minimum avec légendes claires et brève interprétation (une phrase chacun).

5. Parcours EDA — Bloc C : analyses ciblées (bivariées / multivariées)

Idée clé. C’est ici que vous reliez les données au brief. Le croisement de deux variables (bivarié) ou plusieurs (multivarié — par ex. matrice de corrélation ou graphiques conditionnels) permet de dire : « Dans notre échantillon, telle tendance apparaît », avec des réserves sur la causalité.

Méthode. Pour des relations monotones sans hypothèse de ligne droite, la corrélation de Spearman est souvent plus honnête que Pearson sur des scores ordinaux ou des distributions asymétriques. Pour les variables catégorielles, privilégiez les comparaisons par groupe (boxplot de availability_365 selon room_type_code) ou des tableaux croisés. Évitez d’empiler douze corrélations sans fil narratif : gardez deux à quatre figures au cœur du message.

PCA / clusters (optionnel). Avec peu de colonnes dans elysee_tabular, une ACP ou un partitionnement (k-means) peut servir d’exploration pour repérer des profils d’annonces ; présentez-le comme une piste visuelle, pas comme la seule preuve métier. Si vous ne maîtrisez pas encore ces outils, concentrez-vous sur les croisements explicites liés au tableau du bloc A.

Consignes

  1. À partir de votre feuille de route (bloc A), produire au moins deux visualisations qui répondent directement à une question du brief (ex. lien entre multi-annonce et disponibilité ; croisement scores image/texte et type de logement).
  2. Pour chaque figure : une phrase de résultat et une phrase de prudence (biais, corrélation non causale, effectifs faibles dans une catégorie).
  3. Option : une matrice de corrélation (Spearman) sur les variables numériques pertinentes, avec commentaire ciblé sur 2–3 coefficients seulement.
Livrable du bloc C : deux figures « cœur du message » (haute résolution ou export notebook), chacune accompagnée d’une courte légende interprétative (format compréhensible par la Maire : pas de jargon statistique non défini) + un paragraphe de synthèse reliant ces résultats aux hypothèses du Chapitre 1.

6. Parcours EDA — Bloc D : synthèse, limites, rapport et dashboard

Idée clé. L’ingénieur termine par la traçabilité et la communication. La Mairie ne retiendra pas votre code : elle retiendra ce que vous osez conclure et ce que vous refusez d’affirmer faute de preuve. Les limites (périmètre Airbnb, quotas IA, scores −1, absence de certaines variables comme le prix dans cette table si vous ne les avez pas jointes) font partie de la qualité du travail.

Rapport. Structure type : rappel du problème ; données et méthode (en deux pages maximum pour l’EDA) ; résultats illustrés ; discussion (limites, pistes) ; conclusion en trois puces actionnables ou non-actionnables. Longueur cible deux à cinq pages hors annexes, comme annoncé dans la méthodologie globale du module.

Dashboard (Gradio ou équivalent). Un tableau de bord interactif sert de vitrine des analyses déjà validées : quelques filtres (ex. par type de logement), trois ou quatre graphiques reprise du rapport — pas une avalanche de widgets non commentés. Le feature engineering à ce stade est minimal : agrégations, ratios ou scores dérivés déjà justifiés dans les blocs précédents.

Consignes

  1. Rédiger le plan détaillé du rapport (titres de sections + figures prévues).
  2. Rédiger une page « Limites et données manquantes » (biais, généralisation au quartier, interprétation des −1).
  3. Si vous utilisez Gradio : lister les 3 à 4 vues que vous exposerez et le lien avec les figures du rapport (mêmes indicateurs, pas de nouveautés non expliquées).
Livrable du bloc D : le plan structuré du rapport (une page) + le texte des limites (une page maximum) ; si applicable, maquette ou capture du dashboard avec la liste des vues ; préparation du document final à rendre selon les consignes du module (dépôt Git, PDF, etc.).

En résumé : le Chapitre 5 vous fait passer du fichier SQL propre à un récit vérifiable — qualité, descriptif, croisements argumentés, puis synthèse honnête pour le décideur.
